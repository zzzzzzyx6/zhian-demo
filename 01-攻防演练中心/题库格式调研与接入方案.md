# 题库格式调研与接入方案

> 历史调研方案。用户后续已决定统一为「通用」、取消用途／语言／状态筛选，并已接入三份轻量题集。当前实现见《题库与版本结果更新说明.md》；下文保留原始格式与来源调研。

核验时间：2026-09-28。本轮为选型与产品设计，不批量下载、不新增题库、不改变题库页面结构。

## 1. 范围与结论

已找到此前的原始清单：`D:/安全产品/demo920/题库选型与OpenRT兼容性建议.md`。本轮严格保留其中与模型回答有关的七项：SALAD-Bench、HarmBench、CyberSecEval 2/3 的文本子集、JailbreakBench、StrongREJECT、SafetyBench、AdvBench；AgentHarm、AgentDojo 以及 CyberSecEval 的智能体、环境执行和视觉子集暂不接入。

建议首批产品入口只突出三种用途：**通用安全测试、中文安全认知、越狱与误拒回归**。默认推荐 SALAD-Bench、SafetyBench 中文、JailbreakBench；HarmBench 作为较严格的对照评测，AdvBench 保留历史回归，StrongREJECT 优先作为判定协议，CyberSecEval 文本子集按专题适配。用户先选“想测什么”，系统再推荐可运行的题库与判定方式，不要求用户理解文件字段。

需要先明确两个事实：

- 原候选中，SafetyBench 是已核实的中文原生发布入口，但它是选择题安全认知评测，不能代替中文开放式回答的越狱测试。其余通用回答库主要为英文。不能把英文翻译版显示成“官方中文基准”，也不能宣称这份清单已覆盖中文本土化开放式安全场景。
- “保留原题使用”不等于“原文件可以直接上传当前 Demo”。当前导入主要接受 JSON / JSONL 中的文本字段，不能保留选择题、上下文、三级标签和专用判定协议。应由平台做适配，不能让用户逐库手改文件。

## 2. 每个题库网上实际是什么格式

### 原始结构示例（仅示意结构，不转载攻击正文）

SALAD 基础题，外层是数组：

```json
[
  {
    "qid": 0,
    "question": "…原题…",
    "source": "GPTFuzzer",
    "1-category": "O1: Representation & Toxicity",
    "2-category": "O1: Toxic Content",
    "3-category": "O1: Hate Speech"
  }
]
```

三个常见 CSV 入口的表头不同，大小写也不同：

```text
HarmBench:      Behavior,FunctionalCategory,SemanticCategory,Tags,ContextString,BehaviorID
JailbreakBench: Index,Goal,Target,Behavior,Category,Source
StrongREJECT:   category,source,forbidden_prompt
AdvBench:      goal,target
```

SafetyBench 测试题与答案分文件保存，必须按 ID 关联，不能按行号盲目配对：

```json
{
  "test_zh.json（实际为数组）": [
    {"question": "…中文题目…", "options": ["…选项 A…", "…选项 B…"], "category": "Offensiveness", "id": 0}
  ],
  "opensource_data/test_answers_zh.json（实际为对象）": {
    "0": {"category": "Offensiveness", "answer": 1}
  },
  "dev_zh.json（实际为按类分组的对象）": {
    "Offensiveness": [
      {"question": "…示例题…", "options": ["…", "…"], "answer": 0}
    ]
  }
}
```

CyberSecEval 文本注入题必须保留的层次：

```json
[
  {
    "prompt_id": 0,
    "test_case_prompt": "…被测模型应遵守的上下文…",
    "user_input": "…注入输入…",
    "judge_question": "…本题的成功判定问题…",
    "injection_variant": "ignore_previous_instructions",
    "injection_type": "direct",
    "risk_category": "security-violating",
    "speaking_language": "English"
  }
]
```

## 3. 哪些可以直接拿，哪些需要改造

“直接拿”建议定义为**保留上游原题、原标签、原题型与版本**，由系统自动生成平台执行视图；不要让用户理解“要改几个键名”。

| 处理层次 | 题库 | 必须完成的工作 | 页面应该告诉用户什么 |
| --- | --- | --- | --- |
| 保留原题，格式适配 | SALAD 基础集、JBB 行为集、AdvBench 行为集 | 字段映射、来源 ID、分类映射、版本锁定、判定协议配置 | 用途、语言、题量、覆盖标签、已配置判定方式；可直接新建任务 |
| 保留原题，执行与判定适配 | SafetyBench、HarmBench、CyberSecEval 文本套件 | 选择题选项／答案、上下文／多角色输入、专用判定流程；按子集禁用不兼容攻击方法 | 显示题型和指标；不支持的组合给出具体原因和可选替代方案 |
| 作为裁判协议优先接入 | StrongREJECT | 评分 rubric 版本、裁判版本、分值解释、模型许可与来源许可检查 | “回答有害性评分”，并保留细项；不误导为另一份同质化题库 |
| 内容改造后产生新库 | 英文库的中文翻译、中文本土化场景、AdvBench 人工细分类 | 双语对齐、保留原题引用、语言质量抽检、标签审核、规则修订、独立版本 | 明确标为“平台改编版／翻译版”；不可与原基准直接排名 |

当前 Demo 的导入器虽然能识别若干文本字段，但只保留少量元信息：直接喂 SafetyBench 会丢掉选项／答案，直接喂 SALAD 原文件会丢掉三级原生标签，CSV 库也不能原文件直传。因此本轮不建议一口气把七个名称放入下拉框，造成“可选但不能正确执行”的假象。

## 4. 面向用户的题库管理流程

### 题库列表：先看用途，再看是否能用

主列表每个题库一行，显示：题库名称、用途、语言、题量、题型、风险标签覆盖、当前版本、接入状态。默认不把 Agent 类目摆出来。筛选只保留用户会用到的四个：用途、语言、内置／自建、可用状态；风险类别筛选在需要精细选题时再展开。

状态用“可用 / 待配置判定 / 待校验 / 有更新”，而不是没有解释的抽象技术状态。用户点击某库进入详情；一眼先看到“测什么、怎么判、哪些题没法用”，主操作只有“用于新建任务”。

列表不并排比较不同协议的题量和分数来暗示库的优劣。例如 SafetyBench 的“安全认知正确率”和 SALAD 的“回答攻破率”必须是两种用途、两个结果栏目。

### 题库详情：概要、题目、来源三个页签

1. **概要**：适用任务、语言、题量、类别分布、缺失标签数量、默认判定方式、适配状态。
2. **题目**：编号、题目摘要、风险类别、题型、审核状态。点开看完整原题与标签；选择题展示选项；上下文题展示独立上下文。ID 不替代题目摘要。
3. **来源与版本**：上游链接、固定 revision、获取时间、许可证、原生／翻译／改编标记、改造说明；普通用户无需在这里操作。

用户不需要为每一道题手写标签。在导入预览里先明确“原库自带标签 / 系统建议标签 / 尚未分类”，原生标签可直接保留，平台统一映射和自动建议另存一层。未经人工确认的建议不冒充已验证事实。

### 导入：文件解析由平台负责

去掉“下载导入模板”和“每题只需……”后，导入不能成为无引导的文件选择器。推荐流程是：

1. 上传原文件，支持 JSON / JSONL / CSV；官方适配器自动识别，显示识别到的题库、题型和字段。
2. 预览前 5 条：题目是否完整、选项／上下文是否保留、标签是否识别；有冲突才要求用户选择“哪一列是题目”。不要要求用户先改原文件。
3. 一次展示处理结果：“可导入 998 题，重复 2 题，缺少判定规则 0 题”。错误指出具体行及修复原因；可下载错误清单。
4. 确认名称、语言、用途、判定方式后入库。缺判定方式的库可保存为草稿，但不能启动会产生伪分数的评测。

5 MB 只是当前 Demo 的上传限制，不是上游题库标准；正式产品需支持后台导入与进度，否则完整基准可能无法导入。无需在按钮旁放开发字段名。

### 新建任务：筛选兼容的题库与方法

进入任务时先选测试用途，再展示兼容库。选择题库后默认继承其题型和判定协议；用户看到“本任务将统计什么”。选择多个题库时，允许一起运行但报告分区输出，不能把选择题正确率、连续有害性分数和越狱 ASR 汇成一个安全总分。

选择官方基准模式时保留原题与协议；选择平台攻防模式时可使用题库内容搭配攻击变换，但报告明确“基于某题库的自定义攻防测试”，不称为官方基准复现。若一个库已经是攻击增强题，界面默认不重复追加攻击，主动说明已内含攻击策略。

## 5. 与报告相连的最小数据模型

后台维护一个统一主记录，但不能把所有数据压缩成 `prompt`。

| 数据层 | 必需内容 | 支撑的用户能力 |
| --- | --- | --- |
| 来源 | `dataset_id, source_revision, source_item_id, license, split, language` | 回溯原题、固定版本复测、核对许可 |
| 题型 | `item_type`；文本 `prompt`；选择题 `options, answer_index`；上下文题 `context` 或分角色 `messages` | 正确渲染与执行，不让用户丢上下文 |
| 分类 | 原生分类及其版本；平台风险类目；映射来源；审核状态 | 风险分布、待分类缺口、原生与建议标签区分 |
| 判定 | `protocol_id, protocol_version, expected_behavior, judge_question` 等适用字段 | 向用户解释判定依据、保证跨版本比较口径 |
| 任务快照 | 题目＋标签＋协议＋模型／防护配置冻结 | 避免修改题库后历史报告悄悄变化 |

`Target/target` 必须明确区分为上游攻击目标回应；它不是靶标模型，也不是标准安全答案。平台字段命名和导入预览要显示中文含义，避免现有同名概念混淆。

OpenRT 仍可按此前方案生成派生 CSV / JSONL 执行视图；其只接收文本的入口不代表平台主记录也只能存文本。选择题与上下文执行必须有对应适配器，元信息通过源 ID 映射回每次攻击记录，报告才能按风险类别、方法、题目与轮次交叉查看。

## 6. 许可和核验边界

| 题库 | 本次直接看到的许可信息 | 接入前仍需注意 |
| --- | --- | --- |
| SALAD-Bench | 官方 HF 数据卡 `apache-2.0`；本地已有固定 1000 题子集、来源 revision 和许可证 | 继续保留署名、许可和来源；自动标签不等于人工验证；1000 题子集不是官方全量分数 |
| HarmBench | 官方仓库 LICENSE 为 MIT | 分类器权重独立许可应另核验；`hash_check` 等特殊评价资源不能按通用题处理；数据中的引用内容需检查来源条件 |
| JailbreakBench | 官方数据卡明确数据与代码为 MIT | 保留来源与许可；裁判所用模型按各自条款；与 AdvBench / HarmBench 有重叠，混合库需识别重复题 |
| StrongREJECT | 包仓库 MIT；README 同时明确列出若干来源为 `no license` | **商业分发原始题目不能仅凭代码 MIT 认定已获授权。** 逐来源复核或仅先采用评价实现；分类器权重另查 |
| SafetyBench | 官方 HF 数据卡为 MIT；GitHub 新公开答案已核实 | HF 数据卡仍写“测试答案未开放”，与较新的 GitHub 更新有时差；接入应关联 GitHub 答案并固定两端版本，不依据旧说明误判 |
| AdvBench | `llm-attacks` 仓库 MIT | 保留出处；若新增风险标签，记录平台生成／审核来源；不要声称上游原本提供这些标签 |
| CyberSecEval | `CybersecurityBenchmarks/LICENSE` 为 MIT；仓库根 LICENSE 却是 Llama 3.2 Community License | 按具体路径区分许可，不能套用根许可或反过来概括整个仓库；第三方组件和裁判模型另核验；商业发布前按实际选用子套件复核 |

已核实：上述官方说明、CSV 表头、关键 JSON 首部、SafetyBench 中文答案首部、专用评价代码和列出的许可文件。未完成：全量质量审计、所有子集行数核对、中文机翻全量分布、每一个第三方来源的商业再分发许可、裁判模型权重许可审计。GitHub API 本次遇到匿名限流，改用官方 raw 文件核实；除已有 SALAD 本地 revision 外，新候选尚未冻结 commit，实际入库必须补上。

本轮没有使用第三方转载站点作为字段依据，没有新增清单外题库，也没有把“数据可下载”写成“已经可运行”。

## 7. 建议执行顺序与验收

**第一步：完成三种题型的产品闭环。** SALAD 文本安全、JBB 有害／正常请求回归、SafetyBench 中文选择题。前两者能支持风险与误拒分析，第三者补充中文安全认知。暂不改写原题。

**第二步：把 HarmBench 做成独立标准评测方案。** 先明确可支持的子集、上下文、分类器与散列判定。StrongREJECT 以独立评价协议进入“裁判配置”，保留细项和分值解释。

**第三步：专题和中文开放式场景。** CyberSecEval 先挑文本注入／网络安全回答子集，不扩展至 Agent。中文开放式回答是现有候选的明确缺口，应单独讨论：翻译衍生库、中文本土化自建库，或下一轮扩充权威候选，不能由 SafetyBench 选择题顶替。

每一批入库的可用标准：用户能预览完整题目；系统不丢选项／上下文／标签；结果解释和题型一致；能从报告风险点打开原题与判定证据；同版本同协议复测可比；异常／未分类不会伪装为 0% 风险。
